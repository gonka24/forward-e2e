# Working in this repository

This file is the contract for anyone — human or agent — who changes code here.
Read it, then read [`docs/architecture.md`](docs/architecture.md),
[`docs/operations.md`](docs/operations.md), and
[`docs/development.md`](docs/development.md) before touching the runner.

Everything below describes what the code **does today**. Where a rule is only
partly enforced, that is said plainly rather than smoothed over.

---

| `ops/e2e/` | Host CLI wrappers (`run-e2e.sh`, `Run-E2E.ps1`, `build-runner.sh`, `Build-Runner.ps1`). |
| `tests/unit/runner/` | Offline unit tests for both runner layers. |
| `tests/unit/harness/` | Offline unit tests for the harness and release tooling. |
| `tests/integration/local_sources/` | Local Git source acquisition integration tests. |
| `tests/fixtures/` | Deterministic synthetic test fixtures (`tests/fixtures/evidence/`, contract in its `README.md`; identities derived and the boundary fixtures generated by `tests/unit/runner/support/synthetic_evidence.py`, pinned by `tests/unit/runner/test_synthetic_evidence.py`) and the frozen baseline catalog record `tests/fixtures/compatibility/catalog-baseline-8079c0c.json`. |
| `docs/` | Structured architecture, operations, evidence, coverage, validation, development, migration, and licensing documentation. |

There is **no `gonka-overlay/` any more.** Nothing is copied, patched or
committed into a Gonka checkout. Sources, build outputs, test code and network
state live in separate directories; see
[`docs/architecture.md`](docs/architecture.md).

## 2. The import direction is one-way

`forward_e2e.execution.*` may import `forward_e2e.suite.*`. **`forward_e2e.suite.*` must never import
`forward_e2e.execution.*`.** The E2E layer is built on top of the suite runner, so the
reverse edge would be an import cycle.

How the existing code keeps that true:

- The suite runner accepts the handover context object and only reads
  attributes off it — see `SuiteOrchestrator.__init__` in
  `forward_e2e/suite/orchestrator.py` and the `e2e_context` parameters in
  `forward_e2e/suite/adapters.py`. Nothing is imported from `forward_e2e.execution`.
- `forward_e2e/execution/executor.py` imports the orchestrator **lazily**, inside
  `_default_suite_runner`, so planning, listing and reporting never pull in the
  execution machinery.
- No module under `forward_e2e/suite/*.py` contains a `forward_e2e.execution` import, with
  **exactly two tolerated exceptions** that predate the refactoring:
  `forward_e2e/suite/reporter.py` and `forward_e2e/suite/verifier.py` import
  `forward_e2e.execution.file_safety`. That module depends only on
  `execution.errors`, `execution.sources` and `execution.gitio`, none of which
  imports the suite, so there is no cycle. `tests/unit/runner/test_import_direction.py`
  pins the exception list: it fails if a third suite module imports the
  execution layer, if either documented edge disappears without the list being
  updated, or if `file_safety` (or one of its dependencies) grows a suite
  import. Do not widen the list; if you need a shared type, put it in
  `forward_e2e/suite/` (as `forward_e2e/suite/evidence_model.py` does) and
  import it downwards.

### `forward_e2e/execution/context.py` imports nothing from `forward_e2e.suite`

`E2ERunContext` is the handover object between the two layers, so it must be
importable by both. It is allowed `dataclasses`, `pathlib` and `typing` and
nothing else — **no relative imports at all, and no `forward_e2e.*` imports**.

That is why the E2E evidence-model identifier is repeated there as the literal
`E2ERunContext.E2E_EVIDENCE_MODEL` instead of being imported from
`forward_e2e/suite/evidence_model.py`. The duplication is deliberate and is pinned by
`test_e2e_run_context_has_no_ops_a8_imports` in
`tests/unit/runner/test_e2e_executor.py`, which parses the module with `ast` and
fails on any `forward_e2e.suite` import and on any relative import.

`scripts/acceptance_harness.py` repeats the literals (`EVIDENCE_MODEL_IMMUTABLE`,
the only model it produces, plus the historical `EVIDENCE_MODEL_E2E` and
`EVIDENCE_MODEL_LEGACY`, which it recognises only to refuse them) for the same
reason: it is executed standalone inside the runner image and re-entered by
Testermint, where the `forward_e2e` package is not importable.

The current identifiers are:

| Constant | Value | Status |
|---|---|---|
| `EVIDENCE_MODEL_IMMUTABLE` | `a8.evidence/e2e-immutable-source/2` | The only model new packages may declare and the only one graded as proof. |
| `EVIDENCE_MODEL_E2E` | `a8.evidence/e2e-prepared-build/1` | Historical (overlay + prepared commit). Readable, never proof of unmodified sources. |
| `EVIDENCE_MODEL_LEGACY` | `a8.evidence/legacy-overlay/1` | Historical. Readable, never proof. |

The same "load by path" constraint applies to `forward_e2e/suite/source_snapshot.py`: the
harness loads it with `importlib` from a bare path, so it is standard library
only, with no relative and no `forward_e2e.*` imports.

> [!IMPORTANT]
> If you change an evidence-model identifier you must change it in all three
> places: `forward_e2e/suite/evidence_model.py`, `forward_e2e/execution/context.py` and
> `scripts/acceptance_harness.py`.

## 3. Test conventions

```bash
python3 -B -m unittest discover -s tests/unit/runner -p 'test_*.py' -v
python3 -B -m unittest discover -s tests/unit/harness -p 'test_*.py' -v
python3 -B -m unittest discover -s tests/integration/local_sources -p 'test_*.py' -v
```

- **`unittest` only.** There is no `pytest` dependency and no `conftest.py`; do
  not introduce either. Tests are plain `unittest.TestCase` classes.
- Run with `-B` so no `__pycache__` is written into the tree.
- Tests must be **offline**: no external network, Docker, live chain, or host
  toolchain. External boundaries (Git, Docker, subprocess, filesystem roots) are
  mocked; the function under test never is. A controlled HTTP fixture may bind
  only to `127.0.0.1` on an ephemeral port; it must shut down its server and
  must not be described as evidence of external connectivity.
- **Every test module's docstring states fixture provenance and boundary use.**
  If it makes no HTTP calls, end the module docstring with the line

  ```
  All fixtures are synthetic. No network, Docker, or live chain calls.
  ```

  It is a claim about the module, so it belongs in the module docstring and
  nowhere else. A loopback-only module instead ends with:

  ```
  All fixtures are synthetic. No external network, Docker, or live chain calls; HTTP is loopback-only.
  ```
- **Test names are long and behavioural**, describing the fact being proven,
  not the function being called. Existing examples from
  `tests/unit/runner/test_e2e_build_provenance.py`:

  ```
  test_a_runtime_reporting_the_requested_commit_instead_of_the_prepared_one_fails
  test_a_missing_prepared_test_harness_sha_is_not_compensated_by_the_source_sha
  test_a_payload_without_runtime_fails_strict_e2e_verification
  ```

### The binding fixture rule

`tests/unit/runner/real_fixtures.py`, `tests/unit/runner/support/synthetic_evidence.py`
and `tests/fixtures/evidence/README.md` state the rule and are the places to
extend:

| Fixture kind | Requirement |
|---|---|
| Committed synthetic (`tests/fixtures/evidence/`) | Load the exact producer-shaped document bytes from `tests/fixtures/evidence` when a test needs a committed positive baseline. Four documents are identity-scrubbed derivations of former development receipts (every chain identity replaced by a seed derivation, the recorded arithmetic kept; never receipts) and two are generated from code; each says which in `synthetic_fixture.notice`, pinned word for word. Every document carries `"test_fixture_only": true`, which `verify_live_context`, `verify_go_boundary_report` and `verify_wasm_abi_report` all reject outright, so tests strip it in memory only to exercise the inner rules (`real_lock_exact_e_context`, `go_boundary_evidence`, `fixture_artifacts._staged_report`). The `synthetic_fixture` block names producer, producer functions (each must be a top-level definition of that producer; the identity test resolves them) and the revision whose code defines the shape — for the Go report that is the post-relocation `scripts/run_go_boundary.py`, not a commit. Every chain identity is a derivation of the labelled seed in `support/synthetic_evidence.py`; `tests/unit/runner/test_synthetic_evidence.py` re-derives that from the bytes on every run and fails on one Bech32 address of any prefix, one hash, one 32-byte validator key, one timestamp off the synthetic clock in any zone spelling, one declared bound digest the test did not itself recompute, or one host path (`/home/`, `/root/`, `/Users/`, `/private/`, `/tmp/`, `/var/folders/`, `/workspace/`, `/out/`). The two boundary fixtures are generated by `python3 -B tests/unit/runner/support/synthetic_evidence.py` and must stay byte-identical to the generator's output. Never present a committed fixture as live chain execution proof. |
| Programmatic synthetic positive | May mimic the producer's field names, nesting and types, with every value explicitly synthetic: addresses from `synthetic_address(doc, role)`, hashes from `fixture_tx_hash` / `synthetic_hex`, times from `synthetic_timestamp`, run ids `synthetic-<doc>`. The same identity test covers the in-memory contexts of `real_fixtures.py`. Never treat its passing verifier result as live provenance. |
| Negative | Derived from a positive fixture (a `copy.deepcopy`, then one mutation) by changing or deleting **exactly one mandatory fact**, while preserving its classification and shape. Never use a simplified unrelated shape. |

A negative fixture that also differs in shape proves nothing: the test would
pass even if the check under test were deleted. A positive fixture whose
cross-document facts disagree (for example, accounts that do not match the
document's roles) is just as dangerous: negative tests then pass for the
wrong reason, which is why consistency is checked, not assumed.

## 4. Provenance invariants that must never be weakened

These are load-bearing. Do not remove one to make a run go green, and do not
widen an allowlist to route around a failure.

| Invariant | Where it is enforced |
|---|---|
| **Full-SHA-only selection.** No branch, tag, `HEAD`, short SHA or revision expression, anywhere. | `normalize_full_sha` / `build_source_spec` in `forward_e2e/execution/sources.py`; the host wrappers repeat the check (`bridge_local_repo` in `ops/e2e/run-e2e.sh`). |
| **Sources are immutable.** Both product commits are materialised from Git objects and must stay exactly the selected commit (HEAD, tree, tracked bytes, submodules, no added or ignored files) before the build, after the build and after execution. There is no overlay, no prepared commit and no allow-list of paths that may differ. Build outputs, Gradle state, test code and network state live outside the snapshots. | `forward_e2e/suite/source_snapshot.py`; the before/after checks in `execute_plan` and `_verify_post_run_provenance` (`forward_e2e/execution/executor.py`); `Builder.assert_outputs_outside_sources` (`forward_e2e/execution/builder.py`); `run_live` in `scripts/acceptance_harness.py` (writes `source-immutability.json`); `verify_source_immutability_evidence` in `forward_e2e/execution/deployment.py`. |
| **Old plans are not executable.** `run`/`rerun` refuse a lock whose schema is not `e2e/run-lock/2` or which mentions an overlay/prepared commit; old packages are read by format version and classified as historical, never as immutable-source proof. | `assert_lock_executable` / `superseded_lock_markers` in `forward_e2e/execution/runlock.py`; `PlanSchemaSupersededError` in `forward_e2e/execution/errors.py`. |
| **The runner is independent of the targets.** Harness, external Kotlin tests, network templates, catalog and verifier always come from the runner image, never from the contracts checkout or the Gonka checkout. | `RunnerLayout` and `_runner_section` in `forward_e2e/execution/planner.py`; `BoundaryTaskAdapter.resolve_script` and the harness override in `forward_e2e/suite/adapters.py`; `assert_runner_matches_lock` in `forward_e2e/execution/executor.py`. |
| **The lock envelope is immutable.** A lock is written once, is never rewritten, and is verified by content hash on load. | `write_run_lock`, `load_run_lock`, `RunLock.envelope`, `copy_lock_into_run` in `forward_e2e/execution/runlock.py`. Post-build facts go into `build-manifest.json` / `execution-manifest.json`, bound to the lock by `lock_sha256`. |
| **Private dockerd.** The host Docker socket is never mounted; the runner starts its own inner daemon under an exclusive flock, and only `run`/`rerun` may start it. | `DinDSupervisor` in `forward_e2e/suite/supervisor.py`; `_with_inner_dockerd` in `forward_e2e/execution/cli.py` (called only from `cmd_run`). |
| **Ownership cleanup.** Every container a task started is recorded and torn down; the ownership record is evidence. | `perform_runtime_cleanup` in `forward_e2e/suite/runtime.py`; `cleanup-evidence/ownership.json` is re-read by `_verify_post_run_provenance` in `forward_e2e/execution/executor.py`. |
| **Cancellation is an interruption, not a verdict.** A signal stops the running build's process group, partial evidence is kept, and the result is `CANCELLED`. | `Cancellation` in `forward_e2e/execution/cancel.py`; the failure path and tail of `execute_plan`; `RUN_CANCELLED` handling in `_status_from_findings` in `forward_e2e/execution/outcome.py`. |
| **Timeouts are per task and come from the catalog**, and are frozen into the lock. | `timeout_minutes` / `stage_timeout_seconds` / `gradle_timeout_minutes` in `forward_e2e/suite/catalog.py`; `_limits_section` in `forward_e2e/execution/planner.py`; `SubprocessRunner` in `forward_e2e/suite/adapters.py`. |
| **Acceptance is always `NOT_REVIEWED`.** No automated path may award acceptance. | `AcceptanceStatus.NOT_REVIEWED` is the only value written, in `forward_e2e/suite/orchestrator.py` and `forward_e2e/suite/reporter.py`. |
| **`EXPECTED_PROTO_SHA` is never derived from the selected Gonka SHA.** It describes ABI/format compatibility, which is a different claim from "this binary is running". | `expected_proto_sha()` in `scripts/acceptance_harness.py`. The E2E layer never derives `E2E_EXPECTED_PROTO_SHA` from the selected commit; `E2E_*` is treated as a frozen semantic environment variable prefix (`SEMANTIC_ENV_PREFIXES` in `forward_e2e/execution/planner.py`, `apply_semantic_environment` in `forward_e2e/execution/executor.py`), so an ambient value is cleared rather than silently applied. |

Two further rules that follow from the above:

- **A suite result is not an E2E verdict.** `PASSED` for the whole run is
  decided only in `evaluate_run` (`forward_e2e/execution/outcome.py`), which is what `run`,
  `report` and `recover` all call.
- **Absence is never agreement.** A missing document, a missing live context or
  a silent evidence file is `INCOMPLETE`/`MISSING`, never a pass. See
  `verify_deployed_artifacts` in `forward_e2e/execution/deployment.py` and
  `locate_task_evidence` in `forward_e2e/execution/evidence.py`.

## 5. Files hashed into the lock

`forward_e2e/execution/planner.py` defines these lists whose contents are hashed into
`run.lock.json`:

| Constant | Hashed into | Members |
|---|---|---|
| `HARNESS_FILES` | `lock.runner.harness_hash` | `scripts/acceptance_harness.py`, `vendor/contract_release/release.py`, `scripts/run_go_boundary.py`, `scripts/test_wasm_query_boundary.mjs`, `scripts/external_harness.py`, `forward_e2e/suite/source_snapshot.py`, `harness/container_control.py` |
| `VERIFIER_FILES` | `lock.runner.verifier_hash` | `forward_e2e/suite/verifier.py`, `forward_e2e/suite/collector.py`, `forward_e2e/suite/reporter.py`, `forward_e2e/suite/models.py`, `forward_e2e/suite/catalog.py`, **`forward_e2e/suite/evidence_model.py`** |
| `NETWORK_FILES` | `lock.network.config_hashes` | `harness/network/ownership.yml`, `harness/network/nats.yml`, `harness/network/foreign-native-genesis.yml`, `harness/network/genesis/foreign-native-genesis-provision.sh` |
| `EXTERNAL_TEST_DIRS` | `lock.external_tests.trees` / `tests_hash` | every file under `harness/testermint`, `harness/network`, `harness/go_boundary`, `harness/wasm_query_allowlist` |
| `RUNNER_VERSION_FILE` | `lock.runner.runner_version*` | `ops/runner/RUNNER_VERSION` — the runner version, pinned separately from the product commits |

`forward_e2e/suite/evidence_model.py` is in `VERIFIER_FILES` on purpose: it selects which
grading rules apply to a piece of evidence, so editing it changes what "passed"
means.

> [!WARNING]
> **Editing any file in these lists invalidates every existing lock.**
> `hash_runner_files` hashes the path name and the full bytes of each file, and
> `assert_runner_matches_lock` (`forward_e2e/execution/executor.py`) refuses to execute a
> lock whose `harness_hash`, `verifier_hash` or `catalog_hash` no longer match
> this runner. The correct response is to create a new plan, never to relax the
> check.

`hash_runner_files` treats a **missing** file as an error rather than a shorter
hash, so deleting the verifier cannot produce a valid-looking lock.
`RunnerLayout.assert_complete` (`forward_e2e/execution/planner.py`) is the
image-completeness gate that runs before any hashing: it requires every entry
of `HARNESS_FILES`, `VERIFIER_FILES`, `NETWORK_FILES` and `RUNNER_VERSION_FILE`
to be a regular file and every `EXTERNAL_TEST_DIRS` entry to be a directory,
and it refuses a symlink anywhere on those paths (a link could make the lock
describe bytes outside the runner). Because the lists above are its only
input, adding or renaming a file in a list is enough to extend the gate — but
`tests/unit/runner/test_e2e_planner.py` checks the lists against the real
checkout, so a path that does not exist in the repository fails the offline
suite before it can fail inside an image.

The catalog itself is hashed separately by `compute_catalog_hash`
(`forward_e2e/suite/catalog.py`) into `lock.runner.catalog_hash`, with the same
consequence.

## 6. CI runs offline runner tests

`.github/workflows/ci.yml` defines three Python 3.11 suites plus a Compose
syntax check in the `python-offline-runner` job, and a Windows job for the
PowerShell wrapper tests:

```yaml
- name: Run release helper and acceptance harness tests
  run: python3 -B -m unittest discover -s tests/unit/harness -p 'test_*.py' -v

- name: Run suite and E2E runner tests
  run: python3 -B -m unittest discover -s tests/unit/runner -p 'test_*.py' -v

- name: Verify local Git source acquisition
  run: python3 -B -m unittest discover -s tests/integration/local_sources -p 'test_*.py' -v

- name: Validate Docker Compose configuration
  run: docker compose -f ops/runner/compose.yaml config --quiet
```

```yaml
# windows-host-wrapper job
- name: Check Windows host-wrapper behavior
  run: python -B -m unittest discover -s tests/unit/runner -p test_e2e_host_wrappers.py -v
```

When repository GitHub Actions are enabled, all three suites run on pull
requests and pushes to `main` with zero tolerance for failure. A configured
workflow is not evidence that GitHub actually ran it for a particular commit.
Real chain/Docker E2E executions require live infrastructure and are triggered on dedicated release/validation runs rather than every commit.

Consequences you must plan for:

- Run the two offline unit suites and the local Git integration suite shown above before submitting changes.
- Do not claim a written-but-unexecuted test as passing.
- A static-only review is a legitimate state; call it "ready for static review",
  not "verified".

## 7. Changing a document format

Producer and every consumer change **together, in the same change**, along with
the fixtures. See [`docs/evidence.md`](docs/evidence.md) for the full producer/consumer
matrix.

When a new artefact path is added by a producer, add it to
`ALLOWED_ARTIFACT_PATTERNS` in `forward_e2e/suite/collector.py` as well, or it is simply
never copied into the suite and the reporter can only report it as missing.

## 8. Current interface policy

Linux is the execution platform. Only current scenario IDs and `E2E_*` configuration
variables are supported. Do not add aliases, old environment fallbacks, dual
exports, or migration adapters for earlier runner users. Keep integrity checks
and rejection of superseded evidence models.

## 9. House style

- Comments and docstrings explain **why**, especially why a check exists and
  what failure it prevents. Do not delete existing rationale while editing
  around it.
- Errors carry a stable machine-readable `code` and an `exit_code`
  (`forward_e2e/execution/errors.py`). Add a subclass rather than a bare `RuntimeError`.
- Exit codes: `0` success, `1` failure, `2` usage error, `130`/`143` on
  SIGINT/SIGTERM.
- Paths coming out of a document are resolved with `resolve_within`
  (`forward_e2e/execution/sources.py`) before being read or written. Symlinks in evidence
  are refused, not followed.
- Prefer one shared function called by both the online and the offline path over
  two implementations that can drift — `verify_deployed_artifacts` is the model.
